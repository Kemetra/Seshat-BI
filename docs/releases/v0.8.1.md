# Seshat BI -- v0.8.1 patch release candidate

This patch candidate records the changes merged to `main` after the frozen v0.8
release note (`docs/releases/v0.8.md`). It does not rewrite the historical claims
captured there or in any earlier release note.

## Why this patch exists

v0.8.0 published successfully -- the tag, the GitHub Release, and
`seshat-bi==0.8.0` on PyPI are all live. This patch is not a recovery release.

It exists because v0.8.0 shipped a **defect in the bundled governor MCP server**
that is reachable by anyone who installs the plugin: one of the six governor
tools hangs forever instead of answering. Installed users cannot work around it,
and no repository test could have caught it, so it warrants a patch rather than
waiting for the next feature release.

## What this patch fixes

- **The governor MCP server deadlocked on inherited stdin** (issue #557, PR
  #558). `seshat_run_static_check` never returned when the plugin ran the
  governor over stdio: over **11 minutes** with no output, against a
  **12-second** CLI baseline for the identical check.

  `subprocess.run(...)` without an explicit `stdin` gives the child the
  **parent's** stdin. For `seshat mcp` that handle is the live JSON-RPC pipe
  from the client. `git` inherited it and blocked reading it; the parent blocked
  in `communicate()` waiting for `git`; and the pipe could only be fed by the
  MCP client, which was itself waiting for the response. Neither side could
  proceed.

  Confirmed with a `faulthandler` stack dump against a real stdio server:

  ```
  runner.py:34  _git_ls_files  -> subprocess.run -> communicate()  [BLOCKED]
  runner.py:81  build_context
  governor/service.py:203  _static_check
  ```

  Only that one tool hung, because `_static_check` is the only governor tool
  that shells out to git -- the other five read committed YAML and returned
  promptly. The CLI was never affected, because there stdin is a terminal and
  inheriting it is harmless. That difference is the whole 12-seconds-versus-
  forever gap.

  The fix is one `gitutil.run_subprocess` helper that sets
  `stdin=subprocess.DEVNULL` (severing the inheritance) and a default `timeout`
  (so a residual stall fails **loud** rather than hanging), placed in the module
  that already owns git-subprocess policy via `GIT_HARDENING`. Eleven governance
  call sites route through it. The five dbt/dagster execution runners are
  deliberately excluded and the code says why: they invoke user-authored builds
  that legitimately outlive a shared cap, and none is reachable from the
  read-only governor tools.

- **Four stale facts in the public-catalog submission guidance** (PR #556). The
  runbook is copied into an external portal under a verified identity, so a
  wrong path or a wrong capability answer is a submission defect rather than a
  typo. It cited plugin manifest paths at the repository root that do not
  resolve, told the owner to declare no MCP server when both bundles ship
  `seshat-governor`, and gave a skill-count command that silently returned zero
  for the Claude bundle. The shipped Codex bundle README carried the same false
  "activates no ... MCP server" claim; it was corrected at its template and
  regenerated.

## What this patch does not change

- **No new capability, verb, skill, or rule.** Both bundles still carry 21
  skills; the capability inventory is unchanged.
- **No governance behaviour changed.** The read-only guarantees hold exactly as
  before: no tool advances a stage, grants an approval, writes a readiness
  artifact, or emits a score.
- **Spec 138 remains partially implemented.** US2 and US3 are delivered; US1,
  US4, and the external-acceptance half of US5 are outstanding, unchanged by
  this patch.

## Verification

The regression test for #557 spawns the real server and drives it **over a
pipe**, because that is the only shape that reproduces the defect: the existing
in-process governor tests return in 0.2s while the shipped binary hung. It was
verified in both directions -- failing on the unpatched code (60-second timeout,
the deadlock) and passing in 6 seconds on the fix, with a never-hung control
tool passing throughout.

- Full repository suite: **5037 passed, 27 skipped**.
- `seshat check`, `seshat kit-lint`, `seshat semantic-check --repo .`: no
  governance, projection, or semantic drift. `seshat check` reports its
  pre-existing RS1 warning, which requires a named human to recompute audit
  metadata and is not a release blocker.
- `ruff format --check` and `ruff check`: clean across the repository.
- CI on PR #558: 18 checks passed, 1 skipped, 0 failed, including the new
  over-a-pipe test on Linux and macOS.

## Note on MCP acceptance claims

This patch fixes a defect in the bundled MCP server; it does **not** constitute
external acceptance of that server. Spec 138 US1 acceptance (T021-T023) requires
operator-run verification in a clean workspace with no Seshat development
checkout, and that has not been performed. The defect was found on the installed
plugin surface in a development environment, which is partial evidence toward
T021 rather than a substitute for it.

Any public-catalog submission should continue to declare the `seshat-governor`
MCP server (local, read-only, stdio, no auth) and should **not** claim verified
external MCP behaviour.
