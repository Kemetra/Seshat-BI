# Seshat BI -- v2.0

This note records the changes merged after the frozen v1.1 release note. It does
not rewrite the historical claims captured in `docs/releases/v1.1.md` or any
earlier note.

The full per-entry detail (with spec and PR citations) lives in `CHANGELOG.md`;
this note summarizes the shape of the release.

## Why this is 2.0 and not 1.2

Read this before anything else in this note.

**This is a MAJOR bump because two existing CLI contracts changed, not because
the kit grew.** `docs/operations/versioning-policy.md` classifies a change to an
existing verb's output shape or exit-code meaning as MAJOR, and its closing rule
is that ambiguity resolves toward the larger bump, never the smaller one. Two
changes in this range land in that row:

1. **`seshat doctor`'s default text output is reshaped.** The flat
   `[severity] rule_id message (locator)` line per finding is gone, replaced by
   output grouped by rule id with `hint:` lines and a trailing
   `next allowed action:` line. **Any consumer scraping `doctor` stdout will
   break.**
2. **`seshat pbi-mcp preflight` can now exit `2` where it exited `0`.** Server
   identity is now derived from the argument vector, not just the name/command/url,
   and `--readwrite=true` is recognised as write mode.

Neither is an accidental regression. The first trades a human-readable digest for
a machine-readable one and ships **`--format json`** as the supported programmatic
surface. The second closes a real bypass: a `.mcp.json` could alias the official
Power BI MCP server under an unrelated name, invoke it via `npx` in `args`, and
classify as `absent` -- handing the bypass guard a clean verdict while
`--skipconfirmation` sat in the same entry.

**What did NOT change is worth stating as plainly.** No `seshat check` rule id was
added, removed, or renamed, and no existing rule's predicate or severity changed --
`src/seshat/rules/` has zero changed files in this range, and the registered rule-id
set is identical at both refs (measured by extracting every `@register(...)` id at
`v1.1.0` and at the release commit and comparing the sets: no id added, removed, or
renamed). A consumer's `seshat check` verdict on an unchanged repo is
unchanged by this release. The breaking surface is the two CLI contracts above, not
the governance rule set.

## Migration

| If you | Do this |
|---|---|
| parse `seshat doctor` stdout | switch to `seshat doctor --format json` (`{"findings": [...], "finding_count": N}`, with a `repair_hint` per finding) |
| see `pbi-mcp preflight` newly exit `2` | read the verdict -- it is reporting a bypass-shaped `.mcp.json` that was previously invisible. Fix the config; do not pin to 1.1.0 to restore the `0` |
| depend on `seshat check` behavior | no action; the rule set is unchanged |

## What else is in this release

### Studio: governed analyst workbench, operations, and client review

Specs 140 (#695) and 141 (#697), both ratified and accepted 2026-08-21.

Spec 141's security character differs from 140's and the distinction is worth
carrying: **140 guarded a WRITE** (writing a decision is not granting one),
**141 guards a DISCLOSURE**. `contracts/export-boundary.md` separates *softening*
(pending shown as approved), *leaking* (a DSN in an export) and *acting* (a
recovery button that repairs). Read that contract before touching an export path.

Spec 140's 95 per-step boxes are deliberately unmarked -- read its acceptance
record rather than inferring completeness from checkboxes.

### Approval-gated Power BI MCP writes

Spec 149 (#659, with follow-ups #670, #672, #674, #679) ships
`seshat pbi-mcp plan-write` and `seshat pbi-mcp apply` against Microsoft's official
**local** Power BI Modeling MCP -- external, unforked, never vendored, per ADR 0018
(ratified 2026-08-18).

Every precondition is **derived, never accepted as a caller assertion**: committed
passing readiness read at HEAD (not the worktree), a shape-valid named-human
`publish_ready` approval naming the target as a whole token, an allowlisted target
resolved from the committed allowlist, a resolved `--operation` looked up in the
committed approved set rather than free-form mutation text, and a clean tree or a
backup ref that actually holds the target's content. Twelve typed gate blockers,
fail-closed throughout.

**A successful write advances no readiness stage and grants no approval.**
`--skipconfirmation` is refused everywhere.

### Guided setup and capability derivation

Spec 155 (#683, #684) carries derived scope through to approved provisioning,
including `seshat integrations setup --derived`. Spec 153 (#681, #682) derives
needed capabilities from committed project evidence, with declines, satisfied-state
and a technical-evidence path.

### Doctor becomes agent-usable

M8 (#689) is the reason `doctor`'s output changed. It gains machine-readable JSON,
grouped findings, non-mutating repair hints, and the next allowed action. Hints are
**text only** -- nothing there is executed on the user's behalf, and `doctor` still
never modifies a file. The gate-authority pointer is retained and now appears on the
**clean** path too, so the reassuring no-findings output is not the one that
silently drops the Principle-I boundary marker.

`doctor` remains advisory. The `seshat check` exit code is still the only gate.

## Verification posture

141 commits (113 non-merge, 28 merged PRs) since the `v1.1.0` tag.

The breaking-change classification above was derived by diffing the public policy
surfaces against the `v1.1.0` tag -- rule id set, rule predicates and severities,
CLI verbs and flags, exit codes, and exported symbols -- and both breaking findings
were then confirmed by reading the before/after source, not inferred from commit
messages. The rule-set "no change" claim is a measured comparison of the registered
id sets at both refs, not an assumption from an unchanged directory listing.

**The unit suite now runs on Windows in CI** (#698, #699). Before this release,
Windows CI exercised only the CLI first-success journey and never invoked `pytest`,
so a test with a POSIX-locked fixture was green in CI forever and failed only on a
Windows machine (#691 was one instance, fixed in #694). The new leg is non-blocking
while a baseline accumulates, and passed on its first run: 6329 passed, 59 skipped,
776 deselected.
